## 1. Findings that change what Jelena does next

1. **Hard PRBS codes `100` ("PRBS-31") and `011` ("PRBS-23") are Reserved.** Only `001` = PRBS-7 and `010` = PRBS-15 exist, on both TX and RX. VERIFIED: DS1001 p.70 Table 2.34 (TX_PRBS_SEL_I), p.86 Table 2.52 (RX_PRBS_SEL_I), UG1001 p.119–120.
   - Every run that produced `RX_PRBS_ERR_CNT = 0x7FFF` used code 4: REVIEW_20260926 §3.4 "TX_PRBS_SEL=4 (PRBS-31)…RX_PRBS_SEL=4", and the June tops `m2_serdes_link_top.v:12` / `gs_serdes_link_top.v:12` `PRBS_SEL(3'b100)`.
   - The "PRBS-31" label comes from comments in CologneChip's `serdes_lb.v` (L107–115). CologneChip's own `tc_prbs` loops only over `range(0,2)`, i.e. PRBS-7 and PRBS-15 (`serdestool.py:1001`).
   - **This is the first thing to fix.**
2. **The error counter is 15 bits, saturates at 0x7FFF, and never clears by itself.** It is cleared only by the `RX_PRBS_CNT_RESET_I` pin, the `RX_PCS_RESET_I` pin, or regfile 0x2A[9] **while `RX_PRBS_OVR` (0x2A[4]) = 1**. VERIFIED: DS1001 p.86 text and Table 2.53.
   - At 1.25 Gb/s, about 26 µs of non-matching data fills it. So the reset must come **after** `RX_PRBS_LOCKED=1`, in the same write that keeps OVR=1.
   - `gw/ber_top.v:52,60` ties both reset pins to 0.
3. **Today's bit-exact 8b10b link (180/180) runs at 300 Mb/s, not 1.25 Gb/s.**
   - `serdes_lb_dut.v:97-100` uses N1,N2,N3 = 1,2,3 and OUTDIV = 4.
   - f_BRC = 100 MHz·6/4 = 150 MHz, and the line rate is 2·f_BRC = **0.3 Gb/s**. Sources: DS1001 p.56 eq. 2.1, and `serdestool.py:907-909` uses the same formula.
   - That is the minimum data rate in DS1001 p.155 (0.3–5 Gb/s). The DCO is then 600 MHz, **below the specified f_DCO range of 1250–2500 MHz** (p.155). The datasheet contradicts itself here: 0.3 Gb/s is not reachable with an in-spec DCO.
   - ADR-0002 records that only N=1,2,3 locked on our boards. That was measured in July, **before** the CMD_CFGRST fix (REVIEW R2), so it must be re-measured.
4. **1.25 / 2.5 / 5 Gb/s from our 100 MHz LVDS refclk need N1·N2·N3 = 1·5·5 (DCO 2.5 GHz). Only the output divider changes** (table in §3). VERIFIED: the DS worked example (p.56–57) is exactly 100 MHz, 1·5·5, M3=2 = 2.5 Gb/s, FCNTRL 58 for the 80-bit path. No other N combination gives these three rates from 100 MHz.
5. **No GateMate PCIe link-up and no 5 Gb/s result has been published anywhere.**
   - openCologne-PCIE has its PHY checkboxes unticked (README L89–91), and its bring-up screenshots are from a Xilinx card.
   - The best public hardware evidence is CologneChip's 1.25 Gb/s PRBS-7/15 with 0 errors on the EVB (serdestool README log).
   - openCologne-PCIE names **intergalaktik/ulx5m-m2** as its M.2 card (`1.pcb/README.md` L5–12).
6. **8.StressTest has nothing to do with SerDes.** It tests logic, routing and Fmax. Its "errors" are place-and-route failures, not bit errors (appendix A §2.1).
7. **The June 2026 M2/GS SerDes sources were recovered from Nextcloud**: `serdes_link.v`, the M2 and GS tops, `.ccf`, Makefiles and `uart.v`. The July files (`rt_*.v`, the later `serdes_link.v` with REGFILE at L399-405) are **not recoverable** from any source we have. The June 26 README already predicted the VTM P/N swap on both pairs, which Jelena measured today.

## 3. PLL recipes for a 100 MHz LVDS refclk (ULX5M-GS SER_CLK)

The refclk goes to the dedicated `SER_CLK`/`SER_CLK_N` balls with `PLL_REF_SEL=1` (LVDS) and `PLL_REF_RTERM=1`. It needs no fabric connection; nextpnr only needs the pin constraint (S17). Allowed refclk range is 100–125 MHz (DS p.53).

### 3.1 Formulas (VERIFIED, DS p.54–57)

- f_DCO = 100 MHz · N1·N2·N3. The in-spec range is 1250–2500 MHz (p.155).
- f_BRC = f_DCO / M3.
- **Line rate = 2 · f_BRC.**
- PLL_CLK_O = f_BRC / (M1·M4), with M4 = 2 for the 64/80-bit datapath and 1 otherwise.
- `PLL_MAIN_DIVSEL`:
  - [1:0] selects N2: 00→3, 01→2, 10→4, 11→5
  - [2] selects N1: 0→1, 1→2
  - [4:3] selects N3: 00→3, 10→4, 11→5
  - Default 0x1B = 1·5·5
- `PLL_OUT_DIVSEL` selects M3: 00→1, 01→2, 11→4.
- `PLL_FCNTRL` selects M1 (Table 2.17 p.55): 58→20, 26→10.

### 3.2 Recipe table

VERIFIED: the 2.5 G row is the DS example. The others are DERIVED. The 1.25 G row is also what CologneChip's `tc_prbs` runs on the EVB.

| Line rate | N1,N2,N3 (MAIN_DIVSEL) | OUTDIV M3 (OUT_DIVSEL) | f_DCO | 80-bit: FCNTRL / PLL_CLK_O | 40-bit: FCNTRL / PLL_CLK_O | 20-bit: FCNTRL / PLL_CLK_O | regfile 0x51 (80/40-bit) |
|---|---|---|---|---|---|---|---|
| **1.25 Gb/s** | 1,5,5 (0x1B) | 4 (0b11) | 2500 MHz | 58 / 15.625 MHz | 58 / 31.25 MHz | 26 / 62.5 MHz | `0x36FA` |
| **2.5 Gb/s** (PCIe Gen1) | 1,5,5 (0x1B) | 2 (0b01) | 2500 MHz | 58 / 31.25 MHz | 58 / 62.5 MHz | 26 / 125 MHz | `0x16FA` (used by S7) |
| **5.0 Gb/s** (PCIe Gen2) | 1,5,5 (0x1B) | 1 (0b00) | 2500 MHz | 58 / 62.5 MHz | 58 / 125 MHz | 26 / 250 MHz (too fast for fabric) | `0x06FA` |
| 0.3 Gb/s (**what runs today**) | 1,2,3 (0x01) | 4 (0b11) | **600 MHz, out of spec** | 58 / 3.75 MHz | — | — | — |

Notes:
- **FCNTRL 0x0A** (used by liteeth/serdes_gm for 20-bit) is M1 = 5.25 in the DS table but "5" in CologneChip's code comments. Prefer 58 or 26, which agree in every source.
- REVIEW R11 is confirmed: `build_serdes.py` combines FCNTRL 0x0A with N=1,2,3 and declares 1.25 G.
- CONTEXT.md "refclk" (`main_divsel=0x1B=N1,5,5, fcntrl=0x0A, out_divsel=3`) is the liteiclink **20-bit 1.25 G** recipe. It is not what the working DUT uses.
- An in-spec DCO needs N1·N2·N3 ∈ {15, 16, 18, 20, 24, 25}. Only 25 gives exactly 1.25/2.5/5 Gb/s.
- Risk: ADR-0002 says 1·5·5 did not lock on our boards in July, but that was before CMD_CFGRST (REVIEW R2), with no BISC calibration. CologneChip's `start_serdes_pll(..., calib=True)` enables PFDAC/BISC (serdestool L891–979). **Try 1·5·5 again with CFGRST bitstreams and calib=True before concluding anything.** UNVERIFIED on our boards.
- The 5 Gb/s row is DS-only. The only upstream hint is gm_serdes_lb commit ab7ce94 ("prepare 5G tests", 2026-09-03). There is no published result.

## 4. PRBS / BER — why RX_PRBS_ERR_CNT reads 0x7FFF, and how to measure

### 4.1 Counter semantics (VERIFIED, DS p.84–86)

- The checker is self-synchronizing and supports PRBS-7 and PRBS-15 only.
- It sits after the polarity and comma-align stages and before the 8b10b decoder. The TX generator sits after the 8b10b encoder (DS p.50 Fig 2.29 and p.74).
- `RX_PRBS_ERR_CNT`: 0x1F[14:0], 15 bits, saturates at 0x7FFF. `RX_PRBS_LOCKED` is 0x1F[15].
- The counter is cleared by the `RX_PRBS_CNT_RESET_I` pin, the `RX_PCS_RESET_I` pin, or 0x2A[9] (W/C). The register path works **only with 0x2A[4] RX_PRBS_OVR=1**, and OVR itself works only in testmode (0x5C[2]=1).
- The canonical link-quality test (Fig 2.35 p.66) puts the generator on device A and the checker on device B. `RX_PRBS_ERR_O` is available to the fabric.

### 4.2 Ranked causes for our 0x7FFF

| Rank | Cause | Status | Test |
|---|---|---|---|
| 1 | **Reserved PRBS code 100 used** (TX and RX SEL=4) | Reserved is VERIFIED (DS p.70/86). That it caused the symptom is UNVERIFIED. | Repeat with SEL=001 on both ends |
| 2 | Counter saturated before lock and never reset while OVR=1; reset pins tied 0 in `ber_top.v:52,60` | Mechanism VERIFIED | Reset **after** LOCKED=1 in one write: `0x2A ← (1<<9)|(1<<4)|(SEL<<5)`, mask 0x02F0; then 0x1F must read 0x8000 |
| 3 | Generator enabled on the wrong board (in GS↔M2 the RX checks the *partner's* TX) | Mechanism VERIFIED | TX_PRBS on the transmitting board, RX_PRBS on the receiving board |
| 4 | "PMA loopback" through `RX_PMA_LOOPBACK` is **far-end** per DS p.62 Table 2.25. Near-end is `TX_LOOPBACK_OVR` 0x40[10] + `TX_PMA_LOOPBACK` 0x40[1:0]=01. This conflicts with our loopback.py read-back (appendix B §4.2). | DS text VERIFIED; conflict open | Use the vendor near-end sequence (`tc_loopback`) |
| 5 | All-ones read artifact (LOCKED=1 + 0x7FFF = raw 0xFFFF) | UNVERIFIED | Read 0x1F with OVR=1/SEL=0 right after reset. Read a known register before and after. |
| 6 | Comma aligner re-sliding inside PRBS | UNVERIFIED, weak (the vendor has align on and gets 0 errors) | Retry with comma detect off, as in openCologne-PCIE `serdes_top.v:171-174` |
| 7 | Polarity: an inverted PRBS-7/15 stream is 100 % errors. Keep RX_POLARITY=1 (REVIEW R1) and reset *after* any polarity change. | UNVERIFIED | — |

### 4.3 Vendor procedure to reproduce first

`serdestool.py tc_prbs`, local L981–1045 and upstream L1187–1251:
1. Require testmode.
2. Set the 80-bit datapath.
3. Start the PLL with N=1,5,5 / OUTDIV 4 and calib=True.
4. Reset TRX.
5. Write `0x2A ← 0x0210` (mask 0x02F0).
6. Write TX `0x40 ← (SEL<<6)|(1<<5)` (mask 0x01E0).
7. Write RX `0x2A ← (SEL<<5)|(1<<4)` (mask 0x00F0).
8. Wait 10 s, read 0x1F, and expect LOCKED=1 and CNT=0.
9. Pulse `TX_PRBS_FORCE_ERR` 0x40[9] and expect CNT>0 (6–7 in the vendor log).

This test runs on **one device in loopback**. The vendor has no two-board PRBS test. For GS↔M2, split steps 6 and 7 across the two boards, as in DS Fig 2.35.
