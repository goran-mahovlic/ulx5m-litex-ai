## 1. LOOPBACK_SEL (step 1)

`tools/loopback.py` decodes regfile words 0x2A and 0x40 into all loopback bits. Per DS1001 p.62, 0x2A
`RX_PMA/RX_PCS_LOOPBACK` are the **far-end** loopbacks, and 0x40 `TX_PMA_LOOPBACK`/`TX_PCS_LOOPBACK` (with
`TX_LOOPBACK_OVR`) are the **near-end** ones. The tools print one composite value, `LOOPBACK_SEL`, which is 0 only
when every loopback bit is 0, and every raw bit next to it:

```
LOOPBACK_SEL=0 (far:RX_PMA=0 RX_PCS=0 near:TX_PMA=0 TX_PCS=0 RX_OVR=0 TX_OVR=0; 0x2A=0x280C 0x40=0x1018)
```

In every measurement in this report, on both boards, it read `LOOPBACK_SEL=0`, 0x2A=0x280C and 0x40=0x1018.

**What the regfile can and cannot show (measured):**

| Experiment | Regfile reads | Effect on the link |
|---|---|---|
| P1 bitstream, `RX_POLARITY_I=1` port | `RX_POLARITY=0` | data is decoded **with** inversion (DATA_OK 360/360). The field does not mirror the port |
| Bitstream with `LOOPBACK_I=010` on gs (near-end PMA per DS) | `LOOPBACK_SEL=0` | no loop: when m2 TX is idled, gs gets `IDLE_FF` 20/20 |
| Regfile override on gs: `wr 2A 0101 0101` (RX_LOOPBACK_OVR + RX_PMA_LOOPBACK = far-end PMA) | `LOOPBACK_SEL=1 … !! LOOPBACK ACTIVE` | gs stops receiving m2 data. m2 loses gs data (gs TX now loops m2's data back) and stayed down until gs was reloaded |

Conclusion: `LOOPBACK_SEL=0` is necessary, but it is not proof. The proof that there is no loop is the content
(each word carries the sender's ID, §4) together with the idle and cable tests (§5).

## 4. Fabric BER checker (steps 3–4)

### 4.1 Design (`gateware/ber/`)

One 64-bit word (8 × 8b10b symbols = 80 line bits) per word clock:

| Byte | Content | Use |
|---|---|---|
| 0 | K28.5 | word alignment (the checker finds it and realigns bytes across word boundaries) |
| 1 | `{slot[4:0], id[2:0]}` | **sender ID: gs = 5, m2 = 3**. The checker accepts only the other board's ID. 5 and 3 are not bitwise complements, so P/N-inverted data matches neither. Its own ID sets `self_seen`. |
| 2–6 | 40-bit PRBS (x⁴⁰+x³⁸+x²¹+x¹⁹+1, 8 steps per word) | checked bit by bit; a free-running expected value after sync, so one bad word counts once |
| 7 | back-channel byte, `aux[slot]` | 32-byte frame: the sender's own counters (words, error words, error bits, code errors, flags), command byte, number of injected errors, version, configuration |

- The checker counts `word_cnt`, `err_words`, `err_bits` (popcount), `code_err` (`RX_NOT_IN_TABLE` | `RX_DISP_ERR`),
  `loss_cnt`, `synced`, `self_seen`.
- **gs** prints one status line per second on its UART (DirtyJTAG interface 01, pins `IO_NB_B5`/`IO_NA_B6`). The
  line holds its own counters, the 25 MHz time stamp, the TX/RX clock counts, and the latest m2 frame received
  over the back-channel.
- **m2** has no UART. Its counters reach gs in byte 7. gs sends commands the same way.
- UART commands: `z` clears gs, `Z` clears gs and m2, `e` injects one error on gs TX, `E` makes m2 inject one on its TX.
- Clocks: `PLL_CLK_O` and `RX_CLK_O` each go through a CC_BUFG. Crossings use toggle requests and snapshots that
  stay static until the next request.
- Simulation (`gateware/ber/sim/`, iverilog): `tb_ber_link.v` **11/11 PASS** (sync at byte offsets 3 and 0, clean
  channel 0 errors, aux frame intact, own ID gives `self_seen`, 3 injected errors counted as 3 words/3 bits, cable
  pulled gives loss, recovery, clear). `tb_top.v` checks the UART line format against a CC_SERDES stub.

### 4.2 Result at 0.3 Gb/s (26.09.2026 15:59–16:04, gs and m2 = first `ber_top` build, OUTDIV 4)

```
m2->gs synced=1 self=0 loss=0 words=1125251196 errw=0 errb=0 code=0 BER=0 (<6.7e-11 @95%)
gs->m2 synced=1 self=0 loss=0 words=1125251037 errw=0 errb=0 code=0 BER=0 (<6.7e-11 @95%)
JTAG before and after: gs and m2 LOOPBACK_SEL=0, rx: PEER 10/10 distinct=10
```

- 1.125·10⁹ words × 40 checked bits = 4.5·10¹⁰ bits per direction with 0 errors, so BER < 3/4.5·10¹⁰ = 6.7·10⁻¹¹
  (95 %, rule of three). The 8b10b decoder saw 0 code errors on all 80 line bits of every word.
- Negative control (15:57): after `Z`, `e` ×3 and `E` ×5 → m2 `perrw=3 perrb=3`, gs `errw=5 errb=5`, `inj=3`, `pinj=5`.
- The run line printed `t=137.2s rate=675 Mb/s`. That was a tool bug: the 32-bit 25 MHz time stamp wraps after
  171.8 s. `ber_mon.py` now takes the rate and the duration from consecutive 1 s lines (test `test_ber_mon_rates.py`).
  The word count (1.125·10⁹ ≈ 300 s × 3.75·10⁶) is unaffected.
- This run used the first `ber_top` build (m2 ID = 2, commit d43f095 of the lab notes). The current sources change
  the m2 ID to 3 and pipeline the checker. The sweep in §6 re-measures 0.3 Gb/s with the current sources.

2/10 and 1–3/10 reads were `OTHER` (bad data).

**Reading the result:**
- **Highest rate with 0 errors: 1.25 Gb/s**, using the in-spec recipe N=1,5,5 (f_DCO = 2500 MHz), OUTDIV 4.
  1.885·10⁹ words per direction were checked.
- With N=1,2,3 the DCO runs at 600 MHz, below the 1250–2500 MHz in DS1001. The link is clean only at 0.3 Gb/s.
  At 0.6 Gb/s m2→gs already has errors (2.2·10⁻⁴), while gs→m2 is almost clean (8 bit errors). At 1.2 Gb/s both
  directions fail. 1.2 Gb/s with the out-of-spec DCO fails, but 1.25 Gb/s with the in-spec DCO is error-free. So
  the DCO range, not the channel, limits the 1·2·3 recipe.
- **2.5 Gb/s does not work yet.** m2 rarely stays synced (4.3·10⁶ words in 124 s, compared with 3.9·10⁹ possible),
  and gs sees BER 1.8·10⁻⁴ while synced. Possible causes, not yet separated:
  (1) analog settings: all TX pre/post-emphasis are 0 and the RX equalizer is off (`RX_EN_EQA=0`), taken over from
  the 0.3 Gb/s `serdes_lb.v`, over a channel that runs through the CM4 baseboard, the PCIe slot and an adapter;
  (2) fabric timing on gs: the checker's `rclk` Fmax is 32.6 MHz and 2.5 Gb/s needs 31.25 MHz, which is only 4 %
  margin. On m2 the Fmax is 40.3 MHz, yet m2 is the side that fails worse, which points at (1).
- `self=1` in the error runs does **not** mean a loop. With so many corrupted words, some have the ID bits flipped
  to the receiver's own ID. It is set only in runs with millions of errors, never in the clean runs.

ADPLL lock on m2 alone (16:56, gs not sending SerDes): 1·5·5/4, 1·5·5/2 and 1·2·3/1 all give `PLL_LOCKED=1`,
`RX_RESET_DONE 10/10` (`docs/data_20260926/m2_pll_lock_1g2_2g5.txt`). ADR-0002 ("1·5·5 does not lock") was
measured without CFGRST, and with CFGRST it no longer holds.

## 7. Uncertainties
- 2.5 Gb/s: whether the cause is the analog settings (no pre-emphasis/EQ) or the fabric margin on gs (4 %) is not
  separated. Next: TX pre/post and `RX_EN_EQA` over the regfile (TESTMODE=1), and a faster checker
  (40-bit datapath, or a registered popcount tree).
- The 0.3 Gb/s run in §4.2 used the first build (m2 ID 2). The sweep's od4 step repeats it with the current
  sources: 1.14·10⁹ words per direction, 0 errors.

- The cable-pull steps (5, 6) have not been run. They need a person at the boards.
- The regfile cannot show the fabric-port loopback/polarity state (§1). A bitstream with `LOOPBACK_I=010` did not
  produce a loop. Why the port setting had no effect was not investigated.
- The far-end PMA loop override on gs left gs TX → m2 broken until gs was reloaded. This was not investigated further.
- The location of the P/N swap in the chain is not determined.
