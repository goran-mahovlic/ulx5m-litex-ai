## 2. SoC contents

- CPU VexRiscv `standard` @ 20 MHz, ROM 64 KiB (BIOS), SRAM 8 KiB, L2 disabled (see §4).
- SDRAM IS42VM16320E (1.8 V mobile SDR, 64 MiB, 16 bit), LiteDRAM GENSDRPHY, CL2, SDRAM clock = ~sys (DDR output 0/1).
- Serial (BIOS console) on GPIO5 = TX (U4.C12 IO_NB_B5) and GPIO4 = RX (U4.D8 IO_NA_B6), 115200 8N1. On the Pi this is `/dev/ttyACM0` (DirtyJTAG UART bridge).
- Ethernet 1000 Mb/s: own RGMII PHY from phase 1 (`gateware/gbe_phy.py`), LiteEth with hardware ARP/ICMP (ping without a CPU) on 192.168.10.212 (MAC 10:e2:d5:00:00:00) and Etherbone on UDP 1234.
- KSZ9031 state in the CSRs `phy_status0` = {R1, R1F} and `phy_status1` = {RA, RXC counter}. Read over Etherbone: `0x796d0348` (R1F = 0x0348, 1000 Mb/s FD).
- LiteSDCard (SD_CLK/CMD/DAT0–3). No card is inserted: the BIOS has the `sdcard_*` commands, and `sdcard_init` without a card prints nothing (it does not crash the console).
- Option `--boot {none,serial,sdcard,netboot}` (see §6).

## 4. Reasons for the choices (with measurements)

**Sys clock 20 MHz.** Over 25 P&R builds (S4 and S5, seeds 1–14) nextpnr (SPEED model, VDD_CORE 1.1 V) gives a sys fmax from 18.64 to 26.98 MHz, median 20.02 MHz; 13/25 ≥ 20 MHz. The critical path (47 ns) is not in the CPU but in the bus: Etherbone → wishbone decoder → LiteSDCard block2mem. A higher clock would need registers in the bus or removing Etherbone. Speed is not critical (Goran), so 20 MHz stays. MEASURED on the board: memspeed write 8.8 MiB/s, read 4.5 MiB/s.

**CPU VexRiscv standard.** Comparison of the same SoC (seeds 1 and 11):

| Variant | CPE_LT | RAM_HALF | sys fmax (s1 / s11) |
|---|---|---|---|
| minimal | 24 285 (59%) | 40 | 25.05 / 19.98 |
| lite | 25 559 (62%) | 42 | 19.22 / 20.07 |
| standard | 27 874 (68%) | 48 | 20.06 (s5_1) / 20.38 (s5_9) |

A smaller variant does not raise sys fmax (the critical path is outside the CPU), and `standard` has I/D cache and mul/div, so the BIOS and applications run faster. So `standard`, as long as it fits.

**Global nets (4 CC_BUFG).** They are used by `sys` (CPU/SDRAM/LiteEth), `gtx0` (125 MHz TX logic), TXC (PLL CLK90 through BUFG, lesson I6) and `grx` (RXC 125 MHz from pin IO_EB_A7). To make it fit:
- the SDRAM clock is a DDR output ~sys (S2), without its own global net `sys_ps`;
- `ref` 25 MHz carries `clkbuf_inhibit` on `cd_ref.clk` (I14);
- both PLLs are ECONOMY (B3).

**L2 cache disabled.** yosys maps the LiteX L2 tag memory into 11k flip-flops (SRST on the output register), so L2 = 0 (S1).

**Seed 9.** Among the S5 seeds only s5_4 passes all three domains (gtx 134, sys 20.03, grx 132.8 MHz). On the board it still lost `-s 1472` (at that moment Goran was working on the board at the same time). All 7 other seeds gave 40/40 at 1472 and 1000 (`s5sweep`). s5_9 was chosen, with the largest sys margin (20.38 MHz). Its gtx "FAIL" (119 MHz) is a path into CC_DFF.SR (reset synchronizer), not a data path.

## 5. Findings

1. **The S4SD bitstream hangs without an SD card.** The BIOS boot sequence stays at "Booting from boot.json..." and never reaches the console, so S5 = S4 + `BIOS_NO_BOOT`. Today this is done with the option `--boot none`.
2. **Etherbone "not working" was a client bug.** LiteEthEtherbone replies to destination port = 1234 (`liteeth/frontend/etherbone.py`: `dst_port.eq(udp_port)`), not to the sender's source port. `tools/gbe/eb_read.py` now listens on 1234 (like `litex/tools/remote/comm_udp.py`).
3. **Ping 1472 loses frames WHILE mem_test runs.** MEASURED with the tool `tools/gbe/timed.py`: mem_test of 64 MiB takes 78 s (8.6 → 87.0 s). In that window 10–18 of 20 replies arrive per 10 s, and right after "Memtest OK" 20/20. `sdcard_init` causes no losses (20/20). The S3 bitstream has the same loss, so this is not an S5 regression. HYPOTHESIS: simultaneous SDRAM bus switching (SSO/power supply) corrupts the marginal 1G RGMII RX or TX. The Pi undervoltage (F5) is present then too, but it is also present when there are no losses.
4. **Interference with the measurement.** Goran's simultaneous Linux test on the same board (09:15–09:24) gave a double BIOS banner, a busy ttyACM0 and a dead ping. The script now refuses an attempt if ttyACM0 is open somewhere else (`fuser`).
5. **Sending to the BIOS one character at a time (20 ms).** When a command is sent all at once, the BIOS loses characters ("sdcard_init" arrives as "sdId_init").

## 6. Boot source (`--boot`) and netboot

`gateware/target_soc.py --boot {none,serial,sdcard,netboot}` sets the BIOS constants (commit `6316a0c`):

| `--boot` | BIOS | constants |
|---|---|---|
| `none` (default) | console only | `CONFIG_BIOS_NO_BOOT` |
| `serial` | serialboot, then console | `SDCARD_BOOT_DISABLE`, `NET_BOOT_DISABLE` |
| `sdcard` | SD (boot.json/boot.bin) first, then serial | `SDCARD_BOOT_PRIORITY=-1`, `NET_BOOT_DISABLE` |
| `netboot` | TFTP boot.json/boot.bin from `--remote-ip` first, then serial | `NET_BOOT_PRIORITY=-1`, `SDCARD_BOOT_DISABLE`, `CSR_ETHMAC_BASE`, `ETH_PHY_NO_RESET`, `LOCALIP`/`REMOTEIP`/`MACADDR` |

Test: `sim/test_boot_option.py` generates the SoC for each mode (without P&R) and checks `soc.h`/`csr.h`: 4/4 PASS. `--boot none` gives RTL identical to S5s9 (diff .v without comments = 0 lines).

**Netboot next to the hardware stack.** LiteEth MAC in `interface="hybrid"` (the same thing LiteX `add_etherbone(with_ethmac=True)` does). The CPU gets its own MAC 10:e2:d5:00:00:01 and IP 192.168.10.213, and does TFTP to 192.168.10.14. Hardware ARP/ICMP and Etherbone on .212 stay.

**It only fits with VexRiscv lite.** With `standard` (4 CC_MULT) the netboot SoC does not fit:
- 8/8 seeds fail in the placer ("Unable to find legal placement for cell … CPE_FF"), and `--placer-heap-cell-placement-timeout 200000` does not help (4/4);
- with `lite` (0 CC_MULT) P&R passes (seed 9: gtx 127.4 / sys 20.06 / grx 104.3 MHz).

See lesson J7 (instruction #26) and the clean `-nomult` test in §7.

**TFTP server.** There is no TFTP on 192.168.10.50: the RRQ gets no reply. It was set up on the Pi 192.168.10.14 as the systemd service `tftp-litex`:

    /etc/systemd/system/tftp-litex.service:
    ExecStart=/usr/sbin/dnsmasq --keep-in-foreground --conf-file=/dev/null --port=0 --enable-tftp \
              --tftp-root=/srv/tftp --interface=eth0 --bind-interfaces --log-facility=- --user=nobody

- Separate dnsmasq instance: `port=0` means no DNS, and DHCP is not enabled, so it only listens on eth0:69.
- The existing dnsmasq for the Wi-Fi AP (wlan0, `/etc/dnsmasq.d/wifiap.conf`) was not touched.
- `/srv/tftp` (fpga-klaudio:pi, 775) contains `boot.bin` = LiteX demo (`python3 -m litex.soc.software.demo.demo --build-path <netboot build> --mem main_ram`, 6280 B, sha256 `b89a0529…a437390`).

- TFTP does not work from the container, because the reply comes from a new port that Docker NAT does not let through.

## 7. Two addresses on the network (instruction #32)

| Address | MAC | Who replies | What it does |
|---|---|---|---|
| 192.168.10.212 | 10:e2:d5:00:00:00 | hardware stack (no CPU) | ARP, ping (ICMP), Etherbone UDP 1234 |
| 192.168.10.213 | 10:e2:d5:00:00:01 | CPU (hybrid MAC, CPU port) | BIOS TFTP netboot, applications (speedtest), later Linux |

Ping to .213 gets no reply until the CPU runs something with a network stack. The BIOS and the demo have no ICMP; `speedtest.bin` and Linux reply to ARP.

**Output in the BIOS.** NetBoot3 and newer print both ports in the SoC section of the banner:

    Ident:  ULX5M-GS SoC | HW ping/Etherbone 192.168.10.212 (10:e2:d5:00:00:00) | CPU/TFTP 192.168.10.213 (10:e2:d5:00:00:01)

This is done by the local LiteX patch `docs/litex-bios-print-ident.patch` (`CONFIG_BIOS_PRINT_IDENT`), because the LiteX BIOS otherwise only prints the ident on the `ident` command.

**`nb_accept.sh`** records the CPU port traffic with tcpdump, e.g. "CPU port .213: 1 ARP requests, 1 ARP replies to it, 2 TFTP RRQ, 10 frames .213 -> Pi".

**One IP for both: decision NO.** The hardware stack would have to recognise UDP frames that are not Etherbone and forward them to the CPU port as whole Ethernet frames (rebuilding the MAC and IP headers). Also, the CPU would send with the MAC of the hardware stack, so it would share its ARP. That is new RTL in the 1G receive path, on a chip that is already at 71% LT, while the placer fails from ~76% (J7). The risk and cost are larger than the benefit, and the two addresses are documented in the banners and the README.

## 8. Ethernet speed test (instructions #33, #34, #36, #37)

- The application `tools/speedtest/` (`speedtest.bin`, 10 816 B) is started by BIOS netboot via `boot.json`, without a new bitstream:
  - UDP 5002 echo, 5001 sink, 5000 control (`RX`/`RXEND`, `TX <size> <n>`);
  - it replies to the sender's source IP:port, so it also works through NAT.
- The Linux side measures: `eth_speedtest.py`.
- On the Pi (`/home/pi/FPGA`, pi:pi) there are `eth_speedtest.sh`, `eth_speedtest.py`, `netboot_app.sh speedtest|demo|linux`, `README_speedtest.md` and `speedtest.bin`. A copy of `speedtest.bin` is in `/srv/tftp`.
- Command: `ssh pi@192.168.10.14 ~/FPGA/eth_speedtest.sh`.

**Results from the Pi** (eth0 100 Mb/s; CPU port, VexRiscv lite @ 20 MHz; 2000 datagrams, RTT 100):

| Size | RTT min/avg/max (loss) | Pi→FPGA: board (sent) loss | FPGA→Pi: Pi (board) loss |
|---|---|---|---|
| 64 B | 1.20/1.22/2.42 ms (0/100) | 6.10 Mb/s (8.8) 620/2000 | 0.77 Mb/s (0.77) 0/2000 |
| 512 B | 2.41/2.45/2.67 ms (0/100) | 43.03 Mb/s (47.1) 175/2000 | 3.92 Mb/s (3.92) 0/2000 |
| 1472 B | 4.84/4.86/5.06 ms (0/100) | 95.69 Mb/s (110.5) 0/2000 | 6.33 Mb/s (6.33) 0/2000 |

**Hardware path .212** (`sudo ping -f -c 2000`): 64/512/1472 B → 2000/2000, RTT avg 0.223/0.371/0.716 ms.

**Interpretation:**
- Pi→FPGA 1472 B is limited by the Pi's 100 Mb/s link;
- smaller packets are lost because the CPU cannot process the frames fast enough (~12 kpps);
- FPGA→Pi is limited by the CPU, because libliteeth computes CRC32 in software (`HW_PREAMBLE_CRC` is not defined) and copies the frame into an SRAM slot (J11).

**Gigabit host (Goran, dell-home, `ulx_blast` 1472 B, 50,000 datagrams, 8 threads):**
- the host sent 110.2 Mb/s, the board received 43,995 (12% loss) and **measured 95.67 Mb/s**;
- this is the same ceiling as from the Pi (~8.1 kpps × 1472 B), so the limit is the CPU/MAC (lite @ 20 MHz, 2 RX slots), not the link;
- the board does not send PAUSE: LiteEth has no 802.3x, and the KSZ9031 advertisement (REG4 = 0x0001) does not have bits 10/11;
- why the host sends only ~110 Mb/s is not proven (open question, instruction #39).

**Pitfall (J10).** With `irq_setie(1)` (from the LiteX demo template) the application does not see any frame after the BIOS jump. Without interrupts it works.
