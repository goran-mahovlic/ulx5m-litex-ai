# GateMate (CCGM1A1) + KSZ9031 on ULX5M-GS: lessons from TASK-4999

Source: TASK-4999 and TASK-5007, 2026-09-23 and 2026-09-24. Details and raw measurements are in `docs/HW_DIAG_20260923_TASK-4999.md`.
Sessions are listed in `/home/klaudio/app/raid/archive/fpga-sessions/TASK-4999/README.md`.
Each item has one of two tags:
- **VERIFIED**: measured on the board, proven by simulation, or read in the datasheet or schematic. The evidence is given with the item.
- **HYPOTHESIS**: likely, but not proven. Must not be quoted as a fact.

Board names: the **old board** has no X1, so the FPGA drives the XI clock from IO_EB_A3. The **new board** (from 2026-09-24 at 15:39) has X1 soldered,
and the trace to E16 (IO_EB_A3) is cut.

## A. PHY clock and power

| # | Lesson | Status | Evidence |
|---|---|---|---|
| A1 | KSZ9031 XI with an external clock needs at least **2.5 Vpp** with DC coupling, or 1.5 Vpp with a series capacitor. Bank EB is on +1V8, so IO_EB_A3 gives at most 1.8 Vpp, which is **out of spec**. | VERIFIED | DS00002117F p. 66, ch. 10; `tools/kicad_netlist.py` on ulx5m-gs-hw 61b6709 (ETH_CLK = U4.E16 ↔ U14.46, VDD_EB = +1V8) |
| A2 | The marginal XI (1.8 Vpp) is the cause of link flapping and of the "same bitstream, different outcome" finding on the old board. | HYPOTHESIS | consistent with observations: DRIVE=3 no PHY, DRIVE=6 with PHY, flap reg1 0x796F↔0x794B, link 0 with a correct ID. The XI amplitude was not measured |
| A3 | DRIVE=3 on IO_EB_A3 is not enough: the PHY does not answer on MDIO. With DRIVE=6 the PHY ID is readable (0x0022/0x1622). | VERIFIED | diag6, 2026-09-23 at 17:56 (UART output), commit 53e9ba9 |
| A4 | GateMate GPIO is **not 3.3 V tolerant**: VIN max = VDDIO + 0.4 V, and the absolute maximum of VDDIO is 2.75 V. A 3.3 V X1 must not be connected to E16 while E16 is on a 1.8 V bank. | VERIFIED | DS1001, Tables 4.1 and 4.3 (p. 110) |
| A5 | On the new board (X1, E16 cut) IO_EB_A3 is defined neither as input nor as output (`--no-phy-refclk`). | VERIFIED | `grep -c EB_A3 *.ccf` = 0 in all builds since 16:00 |
| A6 | KSZ9031 needs a PHY reset ≥ 10 ms after the clock is stable. LiteEth gave 16 µs (256 cycles) by default; the correct value is 20 ms (`--phy-reset-ms 20`). | VERIFIED | DS Table 7-4 (tSR); code `LiteEthPHYHWReset` |

## B. PLLs (CC_PLL) and core voltage

| # | Lesson | Status | Evidence |
|---|---|---|---|
| B1 | VDD_CORE is selected with jumper J3 (open = 0.9 V, 1-2 = 1.0 V, 2-3 = 1.1 V). PERF_MD in the build must match the real voltage. | VERIFIED | power.kicad_sch (MPM3833) |
| B2 | On the old board, before switching to 1.1 V (2026-09-23), SPEED PLLs never locked (LOCK_IN + fine-tune overflow), but LOWPOWER did. | VERIFIED | JTAG STATUS_PLLx (`tools/jtag_mailbox.py pll`) on diag6/b2/b1/b4 |
| B3 | At 1.1 V only **ECONOMY** locks 4/4 (both slots, two points in time). SPEED is marginal, and LOWPOWER falls into underflow. | VERIFIED | TASK-5007, HW_DIAG "1.1 V" §2, commit 4648d6b |
| B4 | The same bitstream changes PLL state within 30 min (ft moves: 0x0A3 → 0x27B). | VERIFIED | TASK-5007 §2 |
| B5 | LiteX `GateMatePLL` takes `locked` from the raw `USR_PLL_LOCKED` (LOCKED_STDY is not connected), so every lock glitch resets sys and everything in it (PHY reset, MDIO sequencer). | VERIFIED | code; sys PLL ECONOMY LOCKED in only 24/29 JTAG samples (t5007_sys_ec, new board); client's GATEMATE_CLOCKING.md, pitfall 2 |
| B6 | The fix for B5 is `gateware/sticky_lock.py`: lock must be stable for 1 ms, then it stays sticky. PHY reset and MDIO go into the `ref` domain (raw clk25, reset only CC_USR_RSTN). | VERIFIED (sim) | `sim/tb_sticky_lock.py` 6/6 PASS, commit d2b9a9f. Effect on the board not proven |
| B7 | `refclk_oe` in the sys domain: XI has no clock when the sys PLL does not lock. This is the cause of the "diag6 worked yesterday, not today" finding. | VERIFIED | `sim/test_refclk_oe.sh` (RED → GREEN), commit 48207cb |
| B8 | CC_PLL: ft (fine-tune) is set only at acquisition. The information is carried by loss of lock, and re-acquisition takes 0.2–0.5 s. | VERIFIED | fab4 (/2↔/3 every 168 ms → ft always 0x064) |
| B9 | A stopped reference freezes the PLL state (it stays LOCKED). A PLL as a flag is valid only with `one` and `zero` controls in the SAME slot and the SAME build. | VERIFIED | `tools/pll_state.py`, y1/y3 declared invalid |
| B10 | The output of a spare PLL must be used, otherwise the status is stuck. PLL outputs use global nets (4), and with several PLLs nextpnr fails with `CC_BUFG unsupported`. | VERIFIED | builds b18–b34 and diag (`--single-pll`) |

## C. RGMII / MAC / MDIO

| # | Lesson | Status | Evidence |
|---|---|---|---|
| C1 | KSZ9031 **does not add delay on TX**. The MAC must provide TXC shifted relative to TXD/TX_CTL. | VERIFIED | DS00002117F p. 22 |
| C2 | At 100M, TXC must be shifted by 90° (PLL CLK90). In simulation, the same edge and 180° both fail (TX_CTL is sampled on both edges). | VERIFIED (sim) | `sim/tb_txc_phase.py`. Not proven on the board |
| C3 | GateMate allows only one DDR clock per IO bank ("DDR port use signal different than already occupied DDR source"), so CLK90 for TXC goes to the pin directly, without CC_ODDR. | VERIFIED | nextpnr message |
| C4 | An MDIO frame must have **64 rising MDC edges**. With 63 edges the PHY drops every write. | VERIFIED | `tools/uhello/tb_writes3.v`; on the new board after the fix, R4 = 0101 read back (mp2, 18:50) |
| C5 | AN for 100FD only (reg9 = 0x0000, reg4 = 0x0101, reg0 = 0x1200) gives **100 Mb/s FD** on the switch. | VERIFIED | new board, mp2 over UART (18:50): PHYAD = 3, R1 = 796D, R5 = C5E1, R1F = 0328, RXC ≈ 25.0 MHz |
| C6 | PHYAD is 3, even though LED1 and LED2 have 4k7 to GND: the level is pulled up by FETs Q1/Q2 towards the CM4 connector. | VERIFIED | MDIO scan 0–7 (only A3 answers); schematic |
| C7 | In `fixed_100m` mode, the link state from the RGMII in-band status must not be used (S = 2/3 → gigabit framing). | VERIFIED (code) | commit f7a4498 |
| C8 | New board, n1 (ECONOMY, pll90, store-and-forward): ARP and ping with a frame ≤ 60 B pass, with a frame ≥ 62 B they do not. Once, after boot from flash. | VERIFIED (once) | tcpdump, 2026-09-24 at 15:01 BST; not repeated |
| C9 | The 60/62 B threshold is explained by a 10M link with a 25 MHz TXC (the PHY TX FIFO overflows). | **REFUTED** | 2026-09-24 at 20:50: same threshold with proven 100FD (RF = 0328); raw TX of 100 and 200 B frames works (see H6) |
| C10 | A raw RGMII beacon without LiteX (eb3), with a proven 100FD link and RXC 25 MHz, gives **0 frames** on tcpdump. | VERIFIED | eb3, 2026-09-24 around 18:00 BST: UART R1F = 0328, JTAG PLL0 LOCKED 32/32, tcpdump 0 |

## H. Breakthrough on the evening of 2026-09-24 (20:20–21:10 CEST)

| # | Lesson | Status | Evidence |
|---|---|---|---|
| H1 | **A bitstream must start with CMD_CFGRST (`gmpack --reset`).** Without it, a sparse bitstream (only used frames) is written over the configuration of the previous design. `openFPGALoader -r` with DirtyJTAG does not reset the FPGA: SRST is a pulse with no wait, and the connection to RST_N is not proven. Consequences: a "known-good" bitstream stops working, UART has stuck bits, no frames. | VERIFIED | eb50 without `--reset` (20:48) gives 0 frames and 0 B of UART. The same .txt with `--reset` (ETH_GateMateA1_2409_2050_TXC_CFGRST.bit) right after gives 58 frames and clean UART. `gmpack --help`: "--reset: reset all configuration latches with CMD_CFGRST". Commit 7d874f5 (default in target_eth.py) |
| H2 | **TXC from PLL CLK90 goes through fabric** to the pin (CPE X42/X46 → X113, 6.1–6.9 ns), while TXD/TX_CTL leave from IOSEL FFs on the global clock (0.29 ns). The real phase is 90° + a delay that depends on seed and voltage. | VERIFIED | post-route script on eb3 (seed 1) and n1 (seed 7), `getNetinfoRouteDelay`. Simulation (tb_eb50.v): +7 ns → hold 3 ns, +9 ns → < 1 ns, ≥ 10 ns → TX_ER |
| H3 | **io50 TX:** eth_tx = 50 MHz, all TX pins IOSEL FF (`FF_OBF=true`), TXC = IOSEL FF on PLL CLK180, datapath every 2nd cycle (tx_enable = ph) → 90° by construction, margin 10/10 ns. | VERIFIED | eb50: first frames from the FPGA through the switch (20:21). LiteEth: ETH_GateMateA1_2409_2050_LiteEth_CFGRST.bit → PING works (-s 0/18). sim/tb_io50.py PASS (±8 ns) |
| H4 | **nextpnr bug:** a negedge CC_DFF packed into IOSEL (`FF_OBF`) loses CLK_INV. `cleanup()`/`dff_to_cpe()` clears CLK_INV before `pack_io_sel()`, so the IO FF silently runs on the rising edge. Same in master. Workaround: IO FF on posedge of the PLL output CLK180. | VERIFIED | tools/uhello/negff_repro/run.sh → "BUG PRESENT" (nextpnr-0.11.1-31-g3edea68e) |
| H5 | LiteX peppercorn **does not pass the .sdc** to nextpnr (`#pnr_opts += " --sdc"` is commented out), and RGMII IO has no constraints. nextpnr reports the RAMIO→IOSEL delays (DDR select, CLK90 to the pin) as 0.000 ns. "Timing PASS" does not cover RGMII. | VERIFIED | litex/build/colognechip/peppercorn.py l. ~73; delays2.json |
| H6 | Raw TX of long frames works: a beacon of 100 and 200 B → 44 frames each. RX of long frames works: ARP requests 62–1400 B → replies. The LiteEth reply to a frame > 60 B (ping -s ≥ 19) does not go out, regardless of the data pattern. | VERIFIED | ETH_GateMateA1_2409_2102_Beacon_100B/200B.bit; arp_len.py; ping -p 00/ff/55/aa/0f |
| H7 | A store-and-forward PacketFIFO (BRAM) at 50 MHz fails timing: `ph → ready → rd ptr → ADDRB` is 27 ns and is really a single-cycle path. Disable SF for io50. | VERIFIED | io50a: eth_tx 36.98 MHz; io50b without SF: 51.11 MHz |
| H8 | CC_PLL CLK180/CLK270 with `*_DOUB=1` give double frequency. CLK270×2 has rising edges at 90° and 270° of the CLK0 clock. This is an alternative for TXC with a 25 MHz datapath. | VERIFIED (datasheet) | UG1001 Fig. 7.4, p. 109 |
| H9 | openFPGALoader `reset()` for dirtyJtag sends SETSIG SRST (bit 6) low and then high right away, with no wait (the FTDI branch holds 500 µs). pico-dirtyJtag: SRST is an emulated open-drain (default GPIO20, active low, internal pull-up). ULX5M-GS has no RP2040. RST_N (U4.T15) goes to R111 (10k to +1V8), C138 (100 nF, τ ≈ 1 ms), IO_SB_B8 and J2.72/J2.99 (CM4 connector). Which RP2040 GPIO (if any) leads to RST_N is decided by the carrier board. | VERIFIED (source + schematic) / HYPOTHESIS (connection on the carrier board) | openFPGALoader 676e53e colognechip.cpp l. 52, 88–105; pico-dirtyJtag cmd.c l. 249–274, pio_jtag.h l. 62–66; kicad_netlist.py on ulx5m-gs-hw 61b6709 |
| H10 | Regardless of whether SRST reaches RST_N, CMD_CFGRST in the bitstream (H1) clears the configuration without relying on the cable. It is a reliable cure and is therefore enabled by default. | VERIFIED (effect) | H1 |
| H11 | **Threshold > 60 B = LiteEth `last_be` = 0.** LiteEth 40dfb7a moved to the LiteX Packetizer, which does not set `last_be`. With `core_dw == phy_dw == 8` the MAC has no TX LastBE stage, so a frame > 60 B gets FCS = 00000000 (≤ 60 B is saved by the PaddingInserter). Fix: `TXLastBE8` (`last_be = last`) at the input of the MAC TX path. **CORRECTION (REGOČ 2026-09-24 22:30):** the cause is a version mismatch — LiteEth 9654767 needs LiteX ≥ 7fca6dba (18 Sep, `last_be` in the Packetizer), and we have LiteX 52f183ef6 (17 Mar). It is not an upstream bug; the real fix is a LiteX upgrade (see docs/UPSTREAM_ISSUES_draft.md §2). | VERIFIED | RTL sim (Verilator, sim/io50rtl/run.sh): RED -s 19/20/100 FCS 0, GREEN all OK; board: ETH_GateMateA1_2409_2130_LastBE_Fix.bit -s 0…120 5/5. Commit 4ee8c97 |
| H12 | The LiteEth ICMP echo FIFO is 128 B by default, so a ping with more than 120 B of data is dropped by design. `icmp_fifo_depth=2048` allows -s 1472 (MTU). | VERIFIED | sim -s 1000/1472 OK; ETH_GateMateA1_2409_2141_Ping_MTUs13.bit -s 1000/1472 5/5 |
| H13 | The outcome depends on the seed, even though nextpnr reports PASS: io50f seed 8 (eth_tx 50.59 MHz PASS) does not answer at all, while seed 13 works 3/3. nextpnr for GateMate does no hold analysis. RXC (IO_EB_A7) is a fabric clock with ~300 destinations and a delay spread of 1.58–11.17 ns (s8), or 1.58–9.01 ns (s13). | VERIFIED (seed) / HYPOTHESIS (hold on eth_rx) | board 20:40 and 20:41; post-route script rxpath.py (rx_s8.json, rx_s13.json) |
| H14 | With the recommended bitstream, the first ping reply arrives **2.95 s** after the end of the `-r` load (AN 100FD), and after that 100% of replies. | VERIFIED | `ping -D -i 0.2`, 2 measurements: 2.95 s and 2.94 s |
| H15 | **Seed selection rule:** RXC (IO_EB_A7) is a fabric clock, and nextpnr does no hold analysis. In the seed sweep (23 bitstreams, board, CFGRST), in every variant exactly the seeds with the LARGEST `eth_rx_clk` delay to destinations fail. Diagnostic io50f (~300 destinations, 8.1–11.2 ns): only s8 fails (11.17 ns). Production io50p (~50 destinations, 5.6–7.5 ns): s12 and s9 fail (7.54 ns), and all others work. Less logic in the eth_rx domain (no diagnostics) reduces the spread. | VERIFIED (correlation) / HYPOTHESIS (mechanism: hold) | docs/seed_sweep_io50_20260924.txt; ETH_GateMateA1_2409_2204_SeedF_s*/SeedP_s* |

## I. 1000 Mb/s (TASK-5032, 2026-09-24/25, new board)

Result: **ping at 1000 Mb/s** (`bitstreams/ETH_GateMateA1_2509_0211_GbE_Ping1G.bit`, commit 0d94144, tag `gbe-1000m-ping-ok-20260925`).
Design: `gateware/gbe_phy.py` (at 125 MHz only IO registers, a byte aligner and a 32-bit BRAM port; CDC by whole frames through BRAM)
and `gateware/target_gbe.py`. LiteEth stays in sys (20 MHz).

| # | Lesson | Status | Evidence |
|---|---|---|---|
| I1 | **1G on this board IS feasible**: RXC (IO_EB_A7, a non-clock pin) through an explicit CC_BUFG works at 125 MHz. RX alignment A (rising edge = low nibble) without writing MMD2 pad-skew. | VERIFIED | UART: C = 0x6400BD (125.0 MHz), F = D.rx_frames, rx_drops 0, rx_sel 0 (Ping1G, 3 attempts) |
| I2 | KSZ9031 with reg9 = 0x0200, reg4 = 0x0001, reg0 = 0x1200 gives **R1F = 0348** (bit 6 = 1000, bit 3 = FD), RA = 3800 (LP 1000FD, local and remote RX OK). | VERIFIED | UART mdio_core on every 1G bitstream |
| I3 | Writing AN in the 6th MDIO pass (~2 s) restarts AN, so a second 1000BASE-T AN follows. The first reply came at 12.2 / 6.9 / 7.1 s. With the write in the 1st pass (`WRITE_AFTER = 0`) it is 6.07 / 7.15 / 5.47 s. | VERIFIED | Ring10 and Ping1G, 3 attempts each with a dirty bitstream |
| I4 | **The LiteEth MAC does not set `first` on the PHY sink.** A custom PHY that starts a frame only on `sink.first` hangs TX forever (tx_frames 0). | VERIFIED | board Diag13 (D = tx_frames 0, rx 21); sim `tb_gbe_phy.py` with `first = 0` hangs (RED), and passes after the fix |
| I5 | **A reset-less one-hot ring with INIT** (p = 0001) in a PLL clock domain gets stuck: nextpnr carries INIT over (FF_INIT), but the clock glitches while the PLL locks. The cure is a self-correcting ring `p0 <- ~(p0\|p1\|p2)`. | VERIFIED (board) / HYPOTHESIS (mechanism: glitch) | TXfix11: tx_frames 36, tx_emit 0. After the fix Ring10/Ping1G tx_frames = tx_emit. Sim with the broken ring RED → GREEN |
| I6 | **TXC shifted by 90° must go through CC_BUFG.** A PLL output without BUFG is routed through fabric from the PLL (X46) to the pin (X113), 5.8 ns, so TXC falls on the data transition (0 frames). Through BUFG, TXC has 1.72 ns to the CPE in front of the pin, and the ODDR DDR select 1.15 ns (same path type), so CLK90 gives ~2 ns like RGMII-ID. | VERIFIED (nextpnr probe) / on the board the 90° phase through BUFG works | `tools/pnr_probe`-style probe cpein (p2_s13, b90_s9); Ping1G |
| I7 | CC_ODDR: DDR select comes from the global net through a CPE into IOSEL. nextpnr reports the last hop RAMIO → IOSEL as 0.000 ns (not modelled, see H5). Output order is D0 then D1 (UG1001 Fig. 2.12), and nextpnr maps D0 → OUT2 (rising), D1 → OUT1 (`INV_OUT1_CLOCK`). | VERIFIED (source + UG1001 + board) | pack_io.cc; UG1001 p. 42; 1G frames correct |
| I8 | **nextpnr crashes** (`dict::at` in `TimingAnalyser::set_required_time`) in the full design when TXC goes through a LUT (inverter ~CLK, buffer CLK0, mux in `--txc-rotate` mode) and for `--txc-phase 270`. A minimal example (PLL → inverter → pin) does NOT crash, so the trigger is not isolated. | VERIFIED (observation) / HYPOTHESIS (trigger) | p0/p1/p3 × 4 seeds and r1–r19 all crash; p2 (CLK90 directly) works |
| I9 | nextpnr `fpga_mode` changes only the timing model (and the warning for PLL PERF_MD). With VDD_CORE 1.1 V the correct model is SPEED, while the PLLs stay ECONOMY (B3).
